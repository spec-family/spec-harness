# `guard <path...>` and the hooks

May the round write this?

| The path | The answer |
| --- | --- |
| one the brief protects | **Refused**, unless a signed ruling allows it. |
| one in `affectedFiles` | Allowed. |
| anything else | **Outside the scope**: a warning by default, or a question to the person, or a refusal (`outOfScope`: `warn`, `ask`, `deny`). |

**The files the guard runs on.** Some files are the guard itself, or what it takes its trust from: `.git/**` (git's hooks, and the harness's state under `.git/spec-harness`), `.spec-harness.json`, spec-brief's configuration (`.spec-brief.json`, `spec-brief.json`), whose plugins tell its archive which rulings count, Claude Code's project settings (`.claude/settings.json`, `.claude/settings.local.json`), which start the hook or turn every hook off, the installed tools (`node_modules/@spec-family/**`), and the allowed-signers file `rulings.allowedSigners` names. A round has no reason to write one, and an agent that wrote one could turn the guard off.

- By default such a write is decided by the brief as any other file is: outside the scope, a warning. The hint says what the file is, and that `"protectHarness"` holds such a write, where it said the archive reports it: the archive sees what the round commits, and nothing under `.git` or ignored.
- With `"protectHarness": "ask"` or `"deny"` in `.spec-harness.json`, the guard puts the write to the person or refuses it, reason `harness-file`, whatever the brief's scope says, unless a signed ruling allows it. A brief that protects such a file refuses it as before.
- The default becomes `"deny"` in a later minor, announced a minor ahead. Claude Code's settings in your home directory are outside the repository, and no brief governs them.

**A brief spec-brief cannot read whole** holds every write but one to the brief itself: where `spec-brief list --format json` says a problem with the brief's text or front matter as a whole, or with `protectedFiles` or `affectedFiles`, as an inline list left open, a glob it cannot read, UTF-16 or CR-only lines, what the brief protects cannot be told, and spec-brief lists such a field as empty. The write is refused, reason `unreadable-protection`, in spec-brief's words and with the line, and the next step is the brief, which `spec-brief lint` names the problem in; a session that starts says so once. A problem in any other field is not read. It takes spec-brief 0.15.0 or later, the first whose list says which briefs it could not read: an earlier one is read as one that cannot say, not as one that read every brief whole, and `doctor`, under spec-brief's line, and a session's start, where a brief is named, say so; writes are decided as before ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).

Paths are compared as the filesystem spells them, links resolved and case corrected, so `SRC/db/schema.ts` does not walk past a protection on `src/db/schema.ts` on Windows.

On Windows a path through a drive's share on this machine is read as the drive: `\\localhost\C$\work\app\src\db\schema.ts`, the same through `127.0.0.1`, `--1.ipv6-literal.net` or the machine's own name, and the forms `\\?\UNC\localhost\C$\...` and `//localhost/C$/...`, are `C:\work\app\src\db\schema.ts`. A path through any other share on this machine is refused: the share's own configuration names its directory, which can be the repository by another name, and the guard reads nothing that says which. A share on another machine is outside the repository, as before. The hook, `guard` and the server's `check_path` read them alike ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).

A path through a link is decided two ways: as it reads, its `..` taken first, and as the system writes it, which on Linux and macOS reads a `..` from where the link before it leads and follows a link to nothing to the file it names. Each file is decided by the work tree that holds it, and the stricter answer stands, so `deep/../schema.ts`, `deep` a link to `lib/x`, is refused where `lib/**` is protected, in words that say where the link leads. Which of the two Claude Code's tools write, its hooks reference and its permissions page do not say (read 2026-10-24). On Windows, which reads the `..` first, the two are one ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).

- **The write guard covers Claude Code, and Codex and Copilot by their documentation** (below). By their documentation (read 2026-11-12), GitHub Copilot and Cursor also read `.claude/settings.json` and run its hook lines, and neither reads `hook claude`'s answer: Copilot needs `exec` where `init` writes `args`, and holds a write whose hook exits non-zero, so every edit would be held, whatever `hook copilot` answers; Cursor lets a write through for any exit but 2, so every one would go ahead. That is read from the two agents' pages and from running `init`'s line by hand, with `node` and no script, which exits 1; neither agent was run against it. Where the question carries another agent's fields, Cursor's `cursor_version` or Copilot's `toolName` and `toolArgs`, or an event of Cursor's (`preToolUse`) or Gemini CLI's (`BeforeTool`), or a tool the guard does not know that names a file or carries a patch, as Codex's `apply_patch` does, `hook claude` says in one line to the person that the write is not checked, exit 0, and checks nothing for it. git's pre-commit hook, the audit and spec-brief's archive hold for any agent ([ADR-0012](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0012-one-way-into-claude-code.md)).
- **Codex and Copilot.** `hook codex` and `hook copilot` read each agent's question into the tool and the files it writes, decide them as `hook claude` decides a write before it, and answer in the agent's language ([ADR-0012](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0012-one-way-into-claude-code.md), amended 2026-11-12). Read from the agents' own references and source on 2026-11-12, and tested against the shapes they document, not in a live session of either.
  - Codex (`.codex/hooks.json`, `init` writes it): `apply_patch` names no file in a field, so the files are read from the patch's `*** Add File`, `*** Update File`, `*** Delete File` and `*** Move to` lines; a shell command that hands `apply_patch` a heredoc, which Codex applies too, is read the same way. A refusal is Claude Code's `hookSpecificOutput`, with its reason. Codex reads an `ask` as a hook that failed and runs the tool, so where the guard would ask, under `outOfScope: "ask"`, `hook codex` refuses and says the person was to decide.
  - Copilot (`.github/hooks/spec-harness.json`, `init` writes it): `create`, `edit`, `str_replace_editor` and `apply_patch` are read for a file in `path`, `file_path`, `filePath`, `filename` or `file` of `toolArgs`, a JSON string or an object, and in a patch in any argument; Copilot's reference names none of the fields. The answer is `permissionDecision`, `deny` or `ask`, at the top of the object: its CLI asks the person, and its cloud agent refuses. Copilot runs the lines of `.claude/settings.json` as well, above, so in a repository where `init` wrote both, the line there holds every edit.
  - Both run the tool where a hook fails, times out or prints nothing they read. So a question either cannot read, a writing tool that names no file it writes, and a write the guard cannot check are refused, in words, where `hook claude` says them and passes. Neither has a hook after a write that the guard answers: a write outside the scope is not warned of, and the audit and the archive report it.
  - Codex's entry finds the project's install through `git rev-parse --show-toplevel` under a POSIX shell; under `cmd.exe` it runs the script from the session's directory, so a Codex session on Windows starts at the top of the repository.
- **An MCP server's tool that writes a file**, such as a filesystem server's `mcp__fs__write_file`, is read for no path by any of the three hooks: its arguments are the server's own, and `init`'s matchers start no hook for it. The audit and spec-brief's archive report what it wrote, as for a shell's writes.
- `spec-harness hook claude` answers Claude Code's PreToolUse and PostToolUse hooks: a refusal before the write, with the reason and the next step; a warning after a write outside the scope. It never answers `allow`, which would skip the person's own permission prompt. When it cannot answer - the configuration does not load, the briefs cannot be read, the harness meets an error it did not expect - it exits 2, and before a write Claude Code then holds the write.
- While `.spec-harness.json` does not load, a write to that file itself is let through, so that a session can mend it: no decision, so the person's own permission prompt stands, and the line that says why every other write is held, to the person as `systemMessage` and to Claude as `additionalContext`, as `.spec-harness.json: unknown key "outofscope"; ..., so every other write is held until it loads; this write, to /work/app/.spec-harness.json itself, is not checked`. The write is to the file and nothing else as the hook reads a path and as the disk does: a file that stands under that name alone, not a link to one and with no second name, named by every path of the call. A file of the same name elsewhere, a link to it, and the configuration of another work tree than the one that does not load are held as every other write is. After the write the hook loads the file again, and says, exit 2, where it still does not load. While it does not load nothing of it is read, so a brief that protects the file, or an `outOfScope` it sets, does not hold this write; the audit and spec-brief's archive still measure the round's change to it ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).
- A write outside every work tree of the repository is decided as one outside the repository is, whatever holds the writes inside: a brief that is archived, or that spec-brief does not list, whichever names it, and a configuration that does not load. It passes with no word, before the write and after it, and spec-brief is not asked about it; `guard` says it is outside the repository. The work trees are the main one and every linked worktree, as the files git keeps under its common directory name them, and a file of a linked worktree is decided as any other inside, by the worktree that holds it, by the hook, `guard` and the server's `check_path` alike. Where they cannot all be named, a git directory kept apart, an entry git keeps that cannot be read, or a `core.worktree` where the configuration does not load, the write is held as before, and so is a path with a `..` in it, and one that a link outside them, a link to nothing among them, has written into a work tree. A path with a `..` that reads both ways as outside every work tree is held in its own words, that a link before the `..` can lead back into one, with how to write it, where it was held in the words of the brief ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).
- In a worktree, a write is decided by the worktree's brief. Claude Code names the project a session started in, and hands the hook the directory Claude works in as the question's `cwd`: in a worktree session started from the desktop app, and after Claude enters a worktree, the first is the main checkout and the second the worktree. Where `cwd` is in another work tree of the same repository, that work tree's branch names the brief, its briefs and configuration are read, and its siblings are looked for in its own `node_modules` and then the project's, so a worktree with no install is checked with the project's. A path it does not hold, and every path where `cwd` is in another repository or in none, is decided by the project as before ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).
- After a write the hook answers from what it decided before it, for the same call: the run before keeps the warnings it would give under the git common directory, in `spec-harness/calls/`, named by the question's `session_id` and `tool_use_id`, and the run after takes them away and answers with no process started. A refused call keeps nothing, nor one that writes `.spec-harness.json`, spec-brief's configuration, the brief or a file beside it, which are decided again after the write; what no run after a write reads is removed after a day. Under `outOfScope: "ask"` or `"deny"` no write is warned of, and the run after one says nothing with no process started ([ADR-0002](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0002-siblings-through-their-command-lines.md)).
- On a brief's branch the hook asks spec-brief for the briefs, which on Windows is most of what a write waits on. Within a session it keeps spec-brief's answer, where spec-brief's `list` names every input it was read from (`inputs`), under the git common directory in `spec-harness/answers/`, by the work tree, the session, spec-brief's script and version, the command line, and the variables git and Node read; and it gives the answer again while each file on the list has the digest listed, or is still not there, each directory holds the files listed, or is still not there where it was listed as not there, and the git index and ignore files read as listed, with no process started. Anything else starts spec-brief as before: an input that is missing, unreadable or reads otherwise, `keep` not `true`, an answer with no `inputs`, a command `tools` names, and, where the list names what git read, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` or `GIT_COMMON_DIR` set. What is kept is removed after a day; every other command starts spec-brief every time ([ADR-0002](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0002-siblings-through-their-command-lines.md)).
- As a session starts, resumes, is cleared, compacted or forked, `hook claude` answers Claude Code's SessionStart with what would hold every write of the session, in one line, to the person as `systemMessage` and to Claude as `additionalContext`, with the writes it would not hold, one to a file outside every work tree of the repository, as the report at a turn's end says: a configuration that does not load, a brief the line, `SPEC_BRIEF` or the branch names that spec-brief does not list, spec-brief missing or too old where a brief is named, and what is wrong with the hook's own line. Nothing is said where all is well, and it exits 0 whatever it finds: the event cannot block, and the session's start is not to be stopped by it ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).
- With `"turnReport": true` in `.spec-harness.json`, `hook claude` answers Claude Code's `Stop`, which it runs as its main agent finishes a turn: with one `git --no-optional-locks status`, every path the work tree holds changed, a shell's writes among them, that the brief protects or that is outside its scope under the `outOfScope` in force, in the words a write of each is given, twenty by name and how many more, as one `systemMessage`; or nothing. It exits 0 and never has Claude go on. `init` writes the entry with `"async": true`, so the turn waits on none of it and Claude Code hands the report to Claude as the next turn begins; without `async` the person sees it as the turn ends, Claude does not, and the end of the turn waits for it. No ruling is read: a protected file a signed ruling allows is reported, and the audit reads the ruling. The plugin brings no such entry; with it on, `init` says the entry to add ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md), [ADR-0012](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0012-one-way-into-claude-code.md)).
- A run of the hook has 45 seconds for every process it starts, together, and a process it asks a question of, git or spec-brief's list of the briefs, is stopped after 20 seconds, or after what is left of the 45 where that is less: Claude Code cancels the hook at the 60 seconds `init` and the plugin give its entry, and before a write lets the write go ahead, and several processes that each answered inside their 20 seconds could pass that minute together. At either limit the hook says `cannot check this write: spec-brief did not answer within 20 seconds, and was stopped`, or `within the 45 seconds the hook's run is given`, and exits 2, which holds the write; a process the run reaches with nothing left is not started, and said so. Every command gives a question the same time, and a round's work, a diff, a probe's worktree, a sibling's check, ten minutes ([ADR-0002](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0002-siblings-through-their-command-lines.md)).
- `spec-harness hook git` is a pre-commit hook for any agent or none. `init --git-hook` writes it; in a hook of your own it is the line `node node_modules/@spec-family/spec-harness/bin/spec-harness.js hook git`.
- `hook claude` passes over whatever else is on its line that it does not read, as every release has, where every other command [refuses it](command-line.md#an-input-that-names-nothing): its line is in settings a later release cannot rewrite, and exit 2 from it holds every write.
- A `--root` on the hook's line that is a file, or is not there, is a guard that was set up and is off: `hook claude` says so in one line to the person, as `systemMessage`, and exits 0, and the write goes on. It refuses nothing for it. No release wrote a `--root` there; without one the hook reads the project Claude Code names, then the session's directory, and outside a git work tree it has nothing to guard and says nothing.
- A line the hook cannot read - an option no command has, an option left without its value, a `--format` or an `--at` that is none, two values for an option that takes one, `--help` beside `--version` - is said the same way: one line to the person, exit 0, and no write held for it. So is a question the hook cannot read: one that is not JSON or names no event, and a tool that writes a file, `Write`, `Edit`, `MultiEdit` or `NotebookEdit`, that names none as a string in `file_path`, `path` or `notebook_path`, or has no `tool_input`, which passed with no word. A byte order mark before the JSON is read past. A tool the hook does not know is not read for a path, and passes with no word. Exit 2 from `hook claude` is for a write it could not check, never for what is wrong with its own line; and no answer of the hook's is exit 1, which Claude Code counts as a hook that failed, so that `"onFailure": "block"` holds a write only for a hook that did not run ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)). `hook git` stops the commit on such a line, exit 2, where a person reads why.

A guard is a guardrail - an agent that writes through a shell passes it - so the audit and spec-brief's archive are the gates ([ADR-0005](https://github.com/spec-family/spec-harness/blob/main/docs/adr/0005-a-guard-is-a-guardrail.md)).
